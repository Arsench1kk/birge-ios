# Matching lab — дизайн стенда, этап 1

Статус документа: рабочий дизайн этапа 1. Все численные значения сценариев — только технические placeholders для запуска кода, не калибровка спроса и не продуктовые параметры. [из заметок: Thesis/Matching_Problem_Spec.md; Thesis/Experiment_Plan.md] [рекомендация консультанта] [TBD — решить с руководителем]

## 1. Граница модели

Стенд решает batch assignment повторяющихся пассажирских заявок на регулярные hub-to-hub рейсы с назначенным водителем. В этапе 1 нет ML, географического поиска, расстояний, остановок между hubs, платежей, реального пользовательского спроса и основного оптимизатора. Выбор ILP/min-cost assignment — гипотеза для этапа 2, не принятое решение. [из заметок: Thesis/Scope_and_Title.md; Decisions/ADR-006_Thesis_Scope_and_Matching_Approach.md] [решение студента] [гипотеза]

## 2. Сущности и определения

- **Hub** — идентифицируемый узел посадки/высадки. Этап 1 хранит только `hub_id` и название; координаты и пешая доступность вне модели, поскольку дипломный MVP задан как hub-to-hub и геоинтеграция не обязательна. [из заметок: Thesis/Matching_Problem_Spec.md; Thesis/Scope_and_Title.md] [решение студента]
- **Corridor** — упорядоченная пара `origin_hub_id → destination_hub_id`; обратное направление — отдельный коридор. Это фиксирует направление регулярной поездки без моделирования промежуточных остановок. [из заметок: Thesis/Matching_Problem_Spec.md] [рекомендация консультанта]
- **PassengerRequest** — повторяющийся шаблон пассажира: ID, corridor ID, непустой набор дней недели (ISO: понедельник=0…воскресенье=6), окно времени выезда `[earliest, latest]`, предпочтительное время выезда внутри окна. Предпочтительное время нужно, чтобы определить измеримое временное отклонение; наличие такого preference и его интерпретация — TBD для согласования. [из заметок: Thesis/Matching_Problem_Spec.md] [рекомендация консультанта] [TBD — решить с руководителем]
- **RequestInstance** — экземпляр шаблона на конкретную календарную дату горизонта. Это единица назначения; сохраняет ID шаблона, дату, коридор и окно. Расширение не создаёт экземпляр в дату, которая не входит в `days_of_week`. [рекомендация консультанта]
- **Driver** — ID, положительная вместимость в пассажирских местах, множество обслуживаемых коридоров и повторяющиеся доступные слоты. Доступный слот задаёт день недели и интервал времени; назначенный рейс должен целиком помещаться в интервал с учётом длительности. Вместимость без места водителя — модельное соглашение, проверить с руководителем. [из заметок: Thesis/Matching_Problem_Spec.md] [гипотеза] [TBD — решить с руководителем]
- **Trip** — конкретный рейс на дату: коридор, время выезда, длительность, водитель и упорядоченный список назначенных request-instance IDs. Рейс открывается baseline только при обработке первой заявки; отдельное предварительное расписание без пассажиров не создаётся. [рекомендация консультанта]
- **Assignment** — связь request instance → trip → driver с датой и вычисленным отклонением по времени. Результат содержит по одной записи на назначенную заявку; не назначенные экземпляры возвращаются отдельным списком. [из заметок: Thesis/Matching_Problem_Spec.md] [рекомендация консультанта]
- **Cancellation/no-show** — cancellation размечается до запуска solver и исключает экземпляр из доступного спроса; no-show размечается после назначения и не меняет assignment в этапе 1. Перепланирование после отмены/no-show не моделируется. Доли и этот порядок — параметры/упрощение для проверки генератора, политика TBD. [из заметок: Thesis/Experiment_Plan.md] [гипотеза] [TBD — решить с руководителем]

## 3. Горизонт и раскрытие повторов

Горизонт задаётся датой начала и целым числом дней `horizon_days`. Каждая recurring-заявка раскрывается в RequestInstance на каждую дату горизонта, чей день недели входит в шаблон. Driver availability раскрывается аналогично. Горизонт и дата начала конфигурируемы; примеры используют технические placeholders. [из заметок: Thesis/Matching_Problem_Spec.md; Thesis/Experiment_Plan.md] [рекомендация консультанта] [TBD — решить с руководителем]

Для воспроизводимости seed применяется к одному локальному генератору псевдослучайных чисел. Один и тот же YAML после нормализации, seed и версия генератора должны давать идентичный сценарий. Хеш считается от канонического содержимого конфига (SHA-256); версия генератора пишется в Scenario и метаданные результата. [рекомендация консультанта]

## 4. Ограничения валидатора

1. Назначенная заявка существует в Scenario, активна и назначена не более одного раза.
2. Дата рейса совпадает с датой request instance; corridor рейса совпадает с corridor заявки и поддерживается водителем.
3. Время выезда находится внутри включительного окна каждого пассажира рейса: `earliest ≤ departure ≤ latest`.
4. Число назначенных request instances рейсу не выше вместимости водителя; пассажир считается одним местом.
5. Один водитель не ведёт два рейса, интервалы которых `[departure, departure + duration)` пересекаются. Длительность рейса — параметр сценария и едина для рейсов в конфигурации этапа 1.
6. Рейс целиком покрыт доступным слотом водителя в дату рейса.
7. У шаблона заявки не более одного назначения на одну дату и коридор (в модели одна recurring-заявка задаёт один corridor).
8. Коридор ссылается на существующие различные hubs; окна, интервалы, вместимости и длительности корректны.

Отменённый экземпляр не должен назначаться. No-show не аннулирует назначение и отдельно считается по метке synthetic. Валидатор не использует код baseline, поэтому может проверять будущие решатели независимо. Нарушения возвращаются списком с кодом и ссылкой на объект; runner останавливает сохранение результата при любом нарушении. [рекомендация консультанта]

## 5. Временное ожидание / отклонение

Для назначенного request instance отклонение — абсолютная разница в минутах между временем выезда рейса и `preferred_departure_minute`: `abs(trip.departure - request.preferred_departure)`. Знак и отдельно раннее/позднее ожидание на этапе 1 не оцениваются. Выбор абсолютного отклонения и самого предпочтительного времени — рабочая операционализация, а не утверждённая бизнес-метрика; нужно согласовать. ## 6. Baseline: deterministic greedy

Baseline фиксируется до сравнительных запусков так:

1. Отбросить до solver экземпляры, помеченные cancellation; остальные сортировать по `(earliest_departure, preferred_departure, service_date, corridor_id, request_template_id, instance_id)` по возрастанию. Это детерминированный приоритет ранних окон; его справедливость/пригодность TBD, порядок нельзя менять после просмотра результатов без новой версии протокола. [рекомендация консультанта] [гипотеза] [TBD — решить с руководителем]
2. Для очередного экземпляра рассмотреть открытые рейсы той же даты и corridor, где есть место, время рейса входит в окно, водитель поддерживает corridor, слот покрывает поездку и нет временного конфликта у водителя. Если такие рейсы есть — присоединить к рейсу с минимальным `(abs(departure - preferred), departure, driver_id, trip_id)`. Таким образом, совместимый существующий рейс предпочитается созданию нового. [рекомендация консультанта]
3. Если совместимого открытого рейса нет — найти все допустимые пары driver × driver availability slot для даты/corridor, свободные от пересечений, где интервал `[slot_start, slot_end]` вмещает длительность и хотя бы одно время из окна пассажира. Выбрать точку окна, ближайшую к preferred (clamp preferred в допустимый интервал `[max(request.earliest, slot.start), min(request.latest, slot.end-duration)]`); затем кандидата с минимальным `(abs(departure-preferred), departure, driver_id, slot_start)`. Открыть рейс и назначить заявку. [рекомендация консультанта]
4. Если допустимой пары нет, оставить экземпляр неназначенным.
5. Все сортировки используют стабильные ID как последний tie-break; никаких случайных решений в solver нет. [рекомендация консультанта]

В baseline пассажир не может быть назначен повторно в одну дату; поскольку шаблон задаёт один corridor, это одновременно не более одного рейса на дату и corridor. После no-show и отмены перепланирования нет. [из заметок: Thesis/Matching_Problem_Spec.md; Thesis/Experiment_Plan.md] [гипотеза] [TBD — решить с руководителем]

## 7. Метрики

Рассчитываются отдельно на каждом synthetic сценарии:

- **Доля назначенных** = число назначенных активных RequestInstances / число всех активных RequestInstances; если активных заявок нет, значение `null`.
- **Среднее и p95 отклонения по времени** = среднее и nearest-rank 95-й перцентиль абсолютных временных отклонений назначенных пассажиров в минутах; при нуле назначений значения `null`.
- **Загрузка мест** = число назначенных пассажирских мест / сумма вместимостей водителей по открытым рейсам. Если открытых рейсов нет, `null`. Это средняя доля забронированных мест на открытых рейсах; no-show не вычитает уже назначенное место.
- **Неразрешённые заявки** = число активных RequestInstances без Assignment.
- **Время работы** = wall-clock seconds solver call, измеренные `perf_counter`; измерение не включает генерацию, валидацию и запись файлов.
- Дополнительно выводятся количества сгенерированных, отменённых и no-show экземпляров, число рейсов, assigned seats и capacity seats для интерпретации метрик. [из заметок: Thesis/Experiment_Plan.md] [рекомендация консультанта]

Доверительные интервалы, число повторов, порог улучшения и статистический тест остаются TBD. Никакого вывода о качестве основного алгоритма этап 1 не делает. [из заметок: Thesis/Experiment_Plan.md] [TBD — решить с руководителем]

## 8. Интерфейс решателя и runner

Solver — объект с `solve(scenario: Scenario) -> SolverResult`. SolverResult содержит список Trip, Assignment и unassigned request-instance IDs; реализации не пишут файлы и не вызывают валидатор. Runner строит Scenario один раз на пару config × seed, передаёт тот же объект каждому solver, затем независимо валидирует результат каждого, считает метрики и записывает JSON/CSV с метаданными. [рекомендация консультанта]

Метаданные: label `synthetic`, имя сценария, seed, SHA-256 конфигурации, версия генератора, версия стенда из package, git commit (если доступен), UTC timestamp, список solver и их версии. При нарушении runner завершается ошибкой до записи строки результата для соответствующего solver. Сырые JSON результаты сохраняют сценарий и результат solver, CSV содержит строки метрик.
