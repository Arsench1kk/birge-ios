## Область и кандидаты

Пусть `P` — активные экземпляры заявок, `D` — водители, `C` — направленные hub-to-hub коридоры. Каждая заявка `p` имеет дату `a_p`, коридор `c_p`, включительное окно `[e_p,l_p]`, предпочтение `q_p` и идентификатор шаблона. Продолжительность рейса `L` едина в сценарии. Для каждого `(дата, коридор)` построим множество целых минут: все минуты глобальной сетки с шагом `h`, попадающие хотя бы в одно окно, а также начало, конец и предпочтение каждого такого окна и эти три значения ± `h`, если они принадлежат хотя бы одному окну. `h > 0` конфигурируется, PLACEHOLDER. Фактически создаётся рейс `r=(d,c,a,t)` только если водитель обслуживает `c`, хотя бы один активный запрос того же дня/коридора допускает `t`, и весь `[t,t+L)` находится в одном слоте доступности водителя для соответствующего дня недели. Географические расстояния, пересадки и перегон между рейсами не моделируются. [гипотеза] [TBD — решить с руководителем]

Множество содержит не все минуты при `h > 1`: оптимальность относится только к построенному кандидатному множеству, а не автоматически к полному пространству целых минут и не к непрерывному времени. При `h=1` покрыты все целые минуты в допустимых окнах. Отбор кандидатов и неизменный baseline могут иметь разные множества допустимых времён; сравнение по качеству решения должно учитывать это ограничение. [гипотеза] [TBD — решить с руководителем]

## Переменные и ограничения

Для кандидата `r` бинарная `y_r` равна 1, когда рейс открыт; бинарная `x_pr` существует только для заявки того же дня и коридора, когда `e_p ≤ t_r ≤ l_p`. Для каждого рейса `K_d` — вместимость водителя.

1. Для каждого `p`: `sum_r x_pr ≤ 1`.
2. Для каждого `r`: `sum_p x_pr ≤ K_d y_r` и `y_r ≤ sum_p x_pr` — открытый рейс непустой.
3. Для одного `(шаблон, дата, коридор)`: `sum_(p,r) x_pr ≤ 1`, включая случай нескольких экземпляров одного шаблона.
4. Для каждого водителя и даты интервалы открытых рейсов `[t_r,t_r+L)` не пересекаются; CP-SAT реализует это через optional intervals и `NoOverlap`, в том числе между коридорами. Слоты уже учтены при формировании домена.
5. Отменённые заявки исключены; no-show не изменяет назначение. Стабильность времени/водителя на повторах не является ограничением или целью v1 и только измеряется существующими метриками. [гипотеза] [TBD — решить с руководителем]

## Лексикографическая цель и статус

Минимизируем одну целочисленную функцию `A·U + B·T + V`, где `U = |P| − sum(x)` — неназначенные заявки, `T = sum(y)` — рейсы, `V = sum |t_r−q_p| x_pr`. Для валидного минутного домена `0…1439`: `Vmax = 1439·|P|`; поскольку непустые рейсы содержат хотя бы одну заявку, `T ≤ |P|`. Выбираем `B=Vmax+1`, `A=|P|·B+Vmax+1`. Тогда один дополнительный рейс дороже любой возможной разницы в `V`, а одна неназначенная заявка дороже любой разницы в `T` и `V`; целевая функция эквивалентна трём лексикографическим уровням. Пустой спрос обрабатывается отдельно; перед созданием модели проверяются целочисленные границы CP-SAT. Один вызов позволяет сообщать общий статус и границу при заданном лимите времени; весовая функция сама по себе не делает найденное при лимите решение оптимальным. [гипотеза] [TBD — решить с руководителем]

`OPTIMAL` — оптимум на кандидатном множестве доказан; `FEASIBLE` — получено допустимое решение, но доказательства оптимальности нет; `INFEASIBLE`/`UNKNOWN` не являются результатом с реальными назначениями. Модель допускает пустой план, поэтому `INFEASIBLE` при корректном входе не ожидается. Для минимизации весовой цели относительный разрыв `max(0, (objective − best_bound) / max(1, abs(objective)))` — только относительный разрыв весовой цели, не отдельная гарантия по каждому уровню. При отсутствии допустимого решения и для базового решателя gap не вычисляется. Независимый валидатор проверяет каждый SolverResult до сохранения; `UNKNOWN`/`INFEASIBLE` должны учитываться в отчётах отдельно, а их техническое пустое назначение нельзя трактовать как измеренное качество алгоритма. Все параметры и лимиты записываются вместе с результатом. [гипотеза] [TBD — решить с руководителем]

В версии 0.1.0 для начальной подсказки CP-SAT сначала вычислялся и независимо проверялся baseline: если все его рейсы входили в кандидатный домен, использовался полный baseline hint; иначе использовался допустимый пустой план. Домен ради подсказки не расширялся. Время работы решателя включало подготовку домена и подсказки; `time_limit_seconds` ограничивал вызов CP-SAT, а не построение модели. Тип подсказки сохранялся в диагностике. Изменения версии 0.2.0 описаны ниже. [гипотеза] [TBD — решить с руководителем]

## Этап 2.5: независимость дат и начальная точка

При выключенной стабильности ни одно ограничение не связывает разные даты: окна, кандидатные рейсы и назначение экземпляра относятся к его дате; ключ шаблона включает дату; NoOverlap группируется по `(водитель, дата)`. Обозначим допустимые множества дат через `F_d`: общее множество — декартово произведение `∏F_d`. Компоненты цели `U`, `T`, `V` аддитивны по датам. Для максимума назначений сумма индивидуальных максимумов достижима объединением дневных решений и является верхней границей; среди них сумма минимальных по дням `T` достижима и минимальна; затем то же для `V`. Следовательно объединение дневных лексикографических оптимумов — глобальный лексикографический оптимум на том же кандидатном домене. Это утверждение не распространяется на ограничения между датами или цель стабильности, если они будут добавлены. [гипотеза] [TBD — решить с руководителем]

В версии 0.2.0 `ilp_cpsat` — чистая общая модель без hint. `ilp_cpsat+decomposed` решает независимые даты; `ilp_cpsat+warm` дополнительно расширяет домен допустимыми отправлениями baseline, передаёт его как полный `AddHint` и после каждого дня сравнивает найденный ответ с независимо валидированным baseline. Если CP-SAT не нашёл ответ или он хуже baseline, возвращается дневной baseline. Объединение проверяется валидатором и по лексикографической цели не хуже полного baseline. Поэтому статус warm означает статус возвращённого плана: `FEASIBLE` при использовании fallback, а исходные статусы CP-SAT и выбранный источник сохраняются по дням. `OPTIMAL` заявляется только если все дневные модели доказали оптимум. Кандидатное множество warm может быть шире чистого из-за отправлений baseline; сравнение показывает совокупный эффект декомпозиции, hint и гарантированного fallback. Для выделения декомпозиции доступен отдельный чистый режим `ilp_cpsat+decomposed`. [гипотеза] [TBD — решить с руководителем]

Общий лимит поиска делится поровну на даты с активным спросом; сумма переданных в CP-SAT дневных лимитов равна общему бюджету. Построение моделей и Python/OR-Tools накладные расходы этим лимитом не ограничены; записываются отдельно. Глобальный gap не выводится, когда оптимальность не доказана: дневные целевые веса отличаются, поэтому усреднять дневные разрывы нельзя. [гипотеза] [TBD — решить с руководителем]
